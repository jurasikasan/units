# task_board

A task board: projects, tasks with a per-project spoken handle (`ABC-12`), the
flow `DRAFT → TODO → IN_PROGRESS → QA → UAT → DONE` plus `CANCELLED`,
assignees and reporters by nick, dependencies, subtasks, labels and
components. It keeps its own Postgres, names subjects by nick without
resolving them, stores `origin` and `discussion` as links it never opens,
publishes `board_events` and consumes nothing. What it promises is
`CONTRACT.md`; this file is for working inside it.

Doors:

- HTTP on `:8099` under `/api/v1` (`projects`, `tasks`, `labels`), plus
  `/health` (liveness and build version) and `/ready` (Postgres reachable).
- MCP at `/mcp` (`internal/task/mcp.go`): `list_tasks`, `get_task`,
  `create_task`, `give_up`, `set_status`, `set_assignee`, `edit_task`,
  `append_to_description`. It is an adapter over the same `Service`; a refusal
  is the service's sentence, because that sentence is the model's repair
  signal. The acting subject is an argument (`actor`, a nick), which the
  host running the agent is expected to overwrite with the subject whose turn
  it is.
- Events on the Redis stream `board_events`, below.

## HTTP

The spec is `docs/swagger.yaml`, generated by `bash doc.sh`;
`cmd/app/routes_documented_test.go` fails when a registered route and the spec
disagree in either direction. Behaviour the spec cannot carry:

- A task is always born `DRAFT`.
- Edits are `PATCH`; there is no whole-task `PUT`. Status, dependencies,
  assignee and summary are sub-routes, because each is a write with its own rule.
- A task is read by UUID or by handle (`ABC-12`).
- `GET /api/v1/tasks` filters: `project_key`, `origin`, `assignee` (a nick or
  `none`), `status`, `q` (a handle, a bare number, or words of the goal),
  `ready=true`, `open=true` (not `DONE`/`CANCELLED`), `order`. `ready` and `status` together are refused. There is no paging.
- `DELETE` has no status gate and refuses a task that has children.

## Status flow

```
DRAFT ──► TODO ──► IN_PROGRESS ──► QA ──► UAT ──► DONE
                        ▲          │  │     │
                        └──────────┴──┼─────┘   (QA/UAT send work back)
                                      └──► DONE (machine-checked, skips UAT)
any open status ──► CANCELLED ──► DRAFT;  TODO ──► DRAFT
```

The table is `transitions` in `internal/task/model.go`, with the reason for each
edge beside it; the database repeats it as a `CHECK`. A word outside the
vocabulary is a 400; a legal word in an illegal place is a 409 that names what
is reachable.

`IN_PROGRESS → TODO` is not a client move. Only the service makes it: `return`
(the task goes back to its reporter, with a note) and parking (an open
dependency added to work in progress).

- Setting the status a task already has is a no-op 200 — unless the request
  carries `from` and the task is elsewhere, which is a 409. A claim sends `from`.
- The write carries the expected previous status in its `WHERE`; zero rows means
  somebody moved it first, also a 409.
- Moving into `IN_PROGRESS` needs an assignee and no open dependency; the refusal
  names the blockers.

## Dependencies

`blocked_by` is derived in the query, never stored: the handles of dependencies
not `DONE`/`CANCELLED`. A stored copy would need waking every dependent when a
blocker closes, and a missed wake-up there fails silently. `ready=true` is the same
predicate negated, plus no open subtask (a parent is done by its children).

`PUT /tasks/{id}/dependencies` replaces the whole set. A ring is refused.

## Redis: `board_events`

Every status move and assignee write goes out as one entry in the CloudEvents
envelope of `../contracts/events.md`; types and payload are in `CONTRACT.md` §4.

An entry is a wake-up, not the record:

- **Claim with `from`.** Streams deliver at least once; a consumer that acts
  without `from` runs a task twice.
- **Best-effort, after the write.** A failed XADD is logged and the move stands;
  there is no outbox.
- **Capped.** A trimmed entry is a missed wake-up.

So a consumer also looks at the board itself, not only at the stream.

## Migrations

`internal/db/migrations/NNNN_name.sql`, embedded, applied on every boot, each in
its own transaction with its ledger row in `schema_migrations`. Hand-rolled;
the reasoning is at the head of `migrate.go`. A file numbered below one already
applied is a hard error; a version in the database this build lacks is logged.
No down-migrations. To change the schema: write the next-numbered file.

## Config

| variable | default | |
|---|---|---|
| `DATABASE_URL` | — | required; startup pings it and exits if unreachable |
| `PORT` | `8099` | |

| `REDIS_CONNECT_TIMEOUT` | `60s` | how long that wait lasts |

## Run and check

```bash
bash check.sh
bash doc.sh        # regenerate docs/ after a handler change
docker compose -f showcase/compose.yaml up --build --attach demo --attach events --exit-code-from events events demo
```

`showcase/` runs the board on its own Postgres and Redis, walks a task through
the flow over HTTP and reads what went out on `board_events`.
